## 1. Исходная ситуация

У пользователя уже существует работающий исследовательский прототип **ARIADNE** в публичном GitHub-репозитории:

https://github.com/SpatialKnots/Nafion-RAG

Текущий проект начинался как RAG-система по тематике Nafion, но дальнейшая концепция должна быть шире.

ARIADNE не следует позиционировать как:

- «ещё один RAG»;
- «чат с PDF»;
- «нейросеть для Nafion»;
- «локальный ChatGPT».

Целевое позиционирование:

> **ARIADNE — локально разворачиваемая программно-аппаратная система для автоматизированного извлечения, структурирования, верификации и накопления экспериментальных научно-технических данных с обязательной привязкой к первоисточнику.**

Nafion — не конечный предмет продукта, а **первый validation domain**, на котором уже создан и проверяется прототип.

## 4. Центральная продуктовая концепция

Главное отличие:

> **ARIADNE не просто отвечает на вопросы по документам — она превращает документы в проверяемые научные данные.**

Целевая цепочка:

```text
Научная публикация / отчёт / НТД
        ↓
OCR / layout / parsing
        ↓
поиск научных сущностей
        ↓
извлечение экспериментального факта
        ↓
структурирование
        ↓
нормализация
        ↓
проверка
        ↓
Scientific Record
        ↓
provenance до первоисточника
```

### Базовая схема Scientific Record

```text
Material
Composition
Property
Value
Unit
Temperature
Other conditions
Measurement method
Source
Evidence
```

Пример:

```text
Material: Nafion N117
Property: ionic conductivity
Value: 0.082
Unit: S/cm
Temperature: 353.15 K
Source value: 80 °C
RH: 95 %
Method: EIS
Source: DOI / page / Table 2 / row N117
```

## 5. Главное технологическое ноу-хау

Преимущество ARIADNE не должно заключаться в конкретной LLM.

Рабочая концепция:

> **ARIADNE Scientific Verification Engine — система допуска научных данных в базу только после многоэтапной проверки источника, контекста, численного значения, единицы измерения, условий эксперимента и согласованности независимых способов извлечения.**

### 5.1. Error taxonomy

Собственная типология ошибок scientific extraction:

- перепутанная строка таблицы;
- неправильное связывание material-property;
- потерянный множитель;
- неправильная единица;
- перепутанная температура;
- смешение experimental/calculated data;
- перепутанный образец;
- неверная связь figure/caption;
- перенос условия измерения от соседнего объекта;
- извлечение значения без достаточного evidence.

### 5.2. Scientific confidence model

```text
Confidence =
f(
  evidence strength,
  extraction agreement,
  unit validity,
  context completeness,
  cross-checks,
  contradictions,
  provenance quality
)
```

### 5.3. Verification routes

Разные источники проверяются разными маршрутами:

- текст;
- таблица;
- график;
- формула;
- подпись;
- экспериментальный раздел.

### 5.4. Abstention policy

Система должна уметь сказать:

> **«данных недостаточно — запись не принимается».**

### 5.5. Domain adaptation

Рабочая линия переноса:

```text
Nafion
→ ion-conducting polymers
→ solid electrolytes
→ electrode materials
→ oxides / functional materials
```

### 5.6. Active learning

ARIADNE должна выбирать наиболее неопределённые случаи для проверки человеком.

Цель:

> каждый час работы эксперта должен максимально улучшать систему.

## 6. Provenance как принцип

Хранить только итоговое число недостаточно.

Для каждой записи должен сохраняться provenance graph.

```text
ScientificRecord #4382
│
├── Material: Nafion N117
│   └── Evidence: p.6, paragraph 3
│
├── Property: ionic conductivity
│   └── Evidence: Table 2, column 4
│
├── Value: 0.082
│   └── Evidence: Table 2, row N117
│
├── Unit: S/cm
│   └── Evidence: table header
│
├── Temperature: 353.15 K
│   ├── Source value: 80 °C
│   └── Transformation: 80 °C → 353.15 K
│
├── RH: 95 %
├── Extractor confidence
├── Verifier confidence
├── Contradiction checks
└── Source DOI / page / bbox
```

ARIADNE должна объяснять не только:

> «какое значение получено?»,

но и:

> **«откуда оно взялось и какие преобразования были выполнены?»**

## 10. KPI — рабочая версия

KPI разделять на официальные и внутренние.

Не использовать абстрактную «accuracy 95%».

| Блок | Целевой KPI |
|---|---:|
| Рабочий корпус | ≥ 1 000 научных публикаций |
| Успешный ingestion обычных PDF | ≥ 95% |
| Сложные/OCR PDF | ≥ 85% |
| Retrieval Recall@5 | ≥ 0.85 |
| Evidence correctness | ≥ 90% |
| Unsupported claims | ≤ 5% |
| Structured extraction field-level F1 | ≥ 0.85 |
| Корректные Value + Unit | ≥ 90% |
| Нормализация поддерживаемых единиц | ≥ 95% |
| Поддерживаемые таблицы | F1 ≥ 0.85 |
| Structured Scientific Records | ≥ 5 000 |
| Gold dataset | ≥ 200 размеченных публикаций |
| Контрольные вопросы/кейсы | ≥ 250–300 |
| Второй домен | ≥ 200 публикаций |
| Падение F1 при переносе | ≤ 10 п.п. |
| On-premise | полный pipeline без внешнего LLM API |
| Пилот | ≥ 1 развёртывание в ИХТТ |
| РИД | ≥ 1 оформленный РИД |

### Центральный продуктовый KPI

> **Не менее 80% экспериментальных записей поддерживаемых типов должны автоматически преобразовываться в полностью корректную цепочку Material → Property → Value → Unit → Conditions → Source с проверяемым provenance.**

### KPI отказа

> **Корректный отказ ≥ 85% на наборе запросов без достаточного evidence.**

## 13. ARIADNE Box

ARIADNE может продаваться как готовый программно-аппаратный комплекс.

Рабочее название:

> **ARIADNE Box**

### Позиционирование

Не «компьютер с GPU», а:

> **локальная система анализа научно-технической информации, работающая в защищённом контуре заказчика.**

```text
Документы предприятия / НИИ
        ↓
ARIADNE Box
        ↓
локальный OCR / retrieval / LLM / extraction
        ↓
проверяемые данные и ответы
        ↓
ничего не отправляется во внешний API
```

- НИИ;
- университеты;
- промышленные R&D-центры;
- химические предприятия;
- фармацевтика;
- металлургия;
- КБ;
- предприятия с закрытой НТД;
- высокотехнологичные производства.

### После гранта возможны

- ARIADNE Box S;
- ARIADNE Box Pro;
- ARIADNE Server.

В текущем проекте достаточно одной reference configuration.

## 18. IP-стратегия

Рабочая идея:

> **open-core + закрытый Scientific Verification Engine.**

Публичными могут оставаться:

- базовый ingestion;
- базовый RAG;
- часть API;
- UI;
- инфраструктура.

Закрытыми потенциально:

- error taxonomy;
- confidence model;
- verification strategies;
- acceptance/rejection logic;
- domain adaptation procedure;
- calibration;
- специализированные тесты;
- часть правил.

Эту часть можно рассматривать как потенциальное **ноу-хау / секрет производства**, если реально обеспечивается режим конфиденциальности.

Важно:

## 23. Зафиксированные решения

- **ARIADNE ≠ просто RAG.**
- **Nafion ≠ конечный предмет продукта.**
- Центральная ценность — **structured scientific data + verification + provenance**.
- Продукт должен работать **on-premise**.
- ARIADNE Box — перспективная коммерческая форма.
- Cloud/API-demo — инструмент продаж и предварительной оценки.
- Сильные внешние модели — R&D-инструмент, а не обязательная часть продукта.
- Собственную foundation LLM не разрабатываем.
- На первом году ограничиваемся двумя materials-science domains.
- Scientific Verification Engine — главный кандидат на технологическое ноу-хау.
- Hardware около 500 тыс. ₽ рассматривается как экспериментальный узел / prototype ARIADNE Box.
- В заявке нужен технологический прототип, а не просто статья.
- KPI разделяются на retrieval / evidence / extraction / normalization / abstention / transfer / deployment.
- Основная коммерческая формула:

> **не «ИИ отвечает по документам», а «система автоматически превращает документы организации в проверяемые научно-технические данные».**
