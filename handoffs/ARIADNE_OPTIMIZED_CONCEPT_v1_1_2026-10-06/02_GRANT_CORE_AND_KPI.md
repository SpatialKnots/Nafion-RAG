# Grant Core, KPI и дизайн проверки

**Версия:** 1.1. **Дата:** 6 октября 2026 года. **Часовой пояс:** Asia/Yekaterinburg.


## Статус показателей
Ниже — рабочие цели для предзаявочного эксперимента. Окончательные определения, scope и договорные значения согласуются после короткого пилота и до подачи/договора. После фиксации их нельзя молча ослаблять. Никакой показатель не считается достигнутым по этой концепции.

## Единица результата
Scientific Record — одно значение/диапазон/граница свойства определённого образца в определённых условиях. Матрицу «температура × образец» не сворачивать в одну запись. Сопоставимость протонной и литий-ионной проводимости не выводится из одинаковой единицы.

Корректность полной записи требует правильных обязательных полей и связей; неверный образец или условия делают запись ошибочной. Необязательное поле может отсутствовать. Исходные операторы, приблизительность, диапазоны и погрешности сохраняются.

## Корпус и эталон
- Рабочий корпус около 120 публикаций; 300 — stretch.
- Gold 60 публикаций: 30 development, 15 validation, 15 untouched test.
- Цель ≥300 gold-записей, включая ≥100 test; плотность сначала измерить на 10–15 публикациях. Количества финализировать до обязательств.
- ≥100 отрицательных/неоднозначных случаев; естественные и синтетические оценивать отдельно.
- Связанные версии статьи держать в одном split.
- Полностью размечать все подходящие случаи внутри заранее определённого supported scope. Не ограничивать знаменатель найденными top-k фрагментами.
- Напарник независимо размечает весь test и минимум 20% development/validation. Разногласия разрешаются до раскрытия результатов системы.
- Gold не формировать одобрением готовых ответов extractor.

## Рабочие KPI
| Показатель | Цель | Определение |
|---|---:|---|
| Precision полной записи | ≥90% | Правильные machine_checks_passed / все machine_checks_passed до правок эксперта |
| Recall полной записи | ≥60% | Правильные machine_checks_passed / все подходящие gold-записи, включая потери обнаружения |
| Provenance допущенных записей | 100% | Каждое непустое извлечённое поле и обязательная связь имеют проверяемое evidence; преобразования имеют источник и правило |
| Маркировка всех кандидатов | 100% | Поле имеет evidence либо явный статус недостатка/неоднозначности; это отдельный показатель, не замена provenance |
| Correct abstention | ≥85% | Доля корректно не допущенных negative/ambiguous cases; ложные отказы на положительных случаях обязательны в отчёте |
| Экономия времени | ≥30% | Снижение медианного полного времени проверенной таблицы при сопоставимом итоговом качестве |
| Offline | Один полный успешный workflow | Сеть отключена после установки: импорт, извлечение, checks, review, export; внешние API и докачка не требуются |
| Пилот | Один завершённый | Реальная задача, согласованный корпус, пользователь, протокол и отчёт |
| Воспроизводимость | Полный manifest каждого run | Code/schema/model/runtime/parser/prompt/rules/dataset hashes, параметры, дата и результаты |

Страница/точный фрагмент обязательны там, где на них опирается извлечение. Bbox хранить только при достоверном mapping; отсутствие bbox само по себе не отменяет проверяемого текстового evidence. Маркировка «evidence ограничено» не разрешает автоматически допустить неподтверждённое поле.

Отсутствие обязательного условия или неоднозначная привязка переводят запись в needs_review. Никакая запись не считается human_confirmed автоматически.

## Сравнение A/B/C/D
- A: текущий numeric extractor; сравнение только общих полей, без ложного обещания full-record baseline.
- B: фиксированный локальный LLM-extractor со схемой.
- C: тот же B плюс конкретные checks и admission policy.
- D: C плюс review химиком; отдельная оценка полного времени и исправленной таблицы.

Для B/C одинаковые документы, upstream parsing, модель, параметры и бюджет обработки. Если меняются и другие части, эффект verification не отделён; это фиксируется как ограничение. Threshold выбирается на validation, затем замораживается. Test не используют для prompt/rule/model selection.

Отдельно показывать качество всех proposed records, качество допущенных, recall и coverage (допущенные / все предложенные). Сравнивать precision–recall/coverage trade-off, а не объявлять рост precision сам по себе победой. Нужны counts ошибок до/после checks и ложных блокировок.

## Сопоставление и анализ
Одна predicted запись соответствует максимум одной gold-записи и наоборот. Дубликаты дают FP. Неверная запись даёт FP и оставляет нужную gold-запись FN. Реестр эквивалентных единиц, допуски округления и обязательные условия фиксируются до test.

Полезные ablations: убрать unit checks, linkage checks, evidence requirements или abstention по одному. Согласие повторных вызовов одной модели не считается независимым подтверждением.

Отчёт: TP/FP/FN, denominators, coverage, false abstention, ошибки по полям, text/table/OCR, время и память; доверительные интервалы с учётом группировки по статье. ≥90% — целевая точечная оценка, не обещание нижней границы интервала при малой выборке.

## Время и отказ от завышенных обещаний
8–12 сопоставимых задач между двумя химиками; порядок ручного/ассистированного режима сбалансировать, избегать запоминания одних статей. Включать загрузку, чтение, review, исправления и экспорт. Только машинное время не является экономией труда.

При невыполнении precision автоматический допуск не считается успешным. Review-first продукт остаётся полезной возможностью, но невыполненный KPI указывается явно. После раскрытия test новые настройки требуют нового независимого набора для новых заявлений.
