# Генеральный план развития backend без обязательной LLM

## Статус документа

Этот документ задаёт общий порядок дальнейшей разработки backend Nafion-RAG.
Он является планом, а не подтверждением реализации перечисленных функций.

Работа выполняется последовательно, по одному приоритету. Перед началом каждого
приоритета подготавливается отдельный подробный план с API-контрактами,
изменениями данных, критериями приёмки и тестами. Реализация следующего
приоритета начинается только после проверки и отдельного решения пользователя.

## Цель

Пользователь должен иметь возможность:

1. загрузить научные статьи в PDF;
2. автоматически извлечь и проиндексировать их содержимое;
3. задать произвольный тематический вопрос без обязательного использования LLM;
4. получить релевантные статьи и точные фрагменты с указанием страниц;
5. открыть исходный PDF непосредственно на найденной странице;
6. самостоятельно изучить полный первоисточник и соседний контекст.

Целевая цепочка работы:

```text
загрузка PDF
  -> извлечение текста или OCR
  -> сохранение источника и трассировки
  -> автоматическое обновление индекса
  -> hybrid search с фильтрами
  -> группировка результатов по статьям
  -> просмотр контекста
  -> открытие исходного PDF на нужной странице
```

## Зафиксированные ограничения

- LLM не является обязательной частью основного пользовательского сценария.
- Основной результат системы — найденный источник и проверяемый фрагмент, а не
  сгенерированный ответ.
- PostgreSQL остаётся источником истины для статей, страниц, чанков и их
  происхождения.
- Исходные PDF после загрузки остаются неизменяемыми.
- Для каждого результата сохраняются статья, путь к PDF, страница или диапазон
  страниц, тип источника, выбранный текстовый слой и точный фрагмент текста.
- Exact retrieval сохраняется как воспроизводимый базовый метод.
- Изменения схемы данных, извлечения текста, OCR, чанкинга и ранжирования не
  выполняются без явного описания, миграции и проверки.
- Облачные сервисы и внешний поиск метаданных не входят в этот план.

## Текущее основание

На момент создания плана в проекте уже присутствуют exact, semantic и hybrid
retrieval. Hybrid использует результаты лексического и семантического поиска и
сохраняет диагностические данные компонентов. Генеративный слой существует
отдельно, но для описанного пользовательского сценария не является обязательным
и не должен блокировать развитие поиска.

Перед реализацией каждого приоритета текущее состояние повторно проверяется по
исходному коду, тестам, базе данных и локальным артефактам.

## Приоритет 1. Доступ к PDF и найденной странице

### Цель

Связать каждый поисковый результат с фактическим первоисточником и дать
пользователю возможность открыть PDF на найденной странице.

### Планируемые работы

- добавить безопасный endpoint выдачи исходного PDF по идентификатору статьи;
- при необходимости поддержать отдельный доступ к OCR-копии, не подменяя ею
  оригинал;
- добавить endpoint или представление текста конкретной страницы;
- формировать ссылку на PDF с фрагментом `#page=N`;
- добавить действие открытия страницы в поисковом интерфейсе;
- возвращать понятные ошибки для неизвестной статьи, отсутствующего файла и
  недоступного текстового слоя;
- запретить path traversal и выдачу файлов за пределами разрешённых каталогов.

### Критерии готовности

- поисковый результат открывает правильную статью на правильной странице;
- оригинальный PDF передаётся без изменения;
- произвольный путь нельзя передать через API;
- отсутствующие записи и файлы дают диагностируемый `404`;
- поведение покрыто API- и UI-тестами.

## Приоритет 2. API загрузки и задания ingestion

### Цель

Убрать необходимость ручного запуска CLI для обычного добавления статей.

### Планируемые работы

- добавить multipart API для загрузки одного или нескольких PDF;
- проверять расширение, MIME-тип, сигнатуру файла, размер и SHA-256;
- сохранять загрузку во временную область до успешной валидации;
- использовать существующий ingestion pipeline без дублирования его логики;
- ставить обработку в очередь через `IngestionJob` и worker;
- определить состояния `queued`, `processing`, `indexed`, `duplicate` и
  `failed`;
- добавить API получения статуса и диагностик задания;
- обеспечить идемпотентное поведение при повторной загрузке того же PDF;
- удалить только временные файлы после ошибки, не затрагивая оригиналы уже
  принятых статей.

### Критерии готовности

- валидный PDF загружается и доходит до состояния `indexed`;
- дубликат определяется по контрольной сумме;
- повреждённый или неподдерживаемый файл не попадает в корпус;
- ошибка extraction/OCR доступна через статус задания;
- перезапуск worker не создаёт дубликаты и не теряет задания.

## Приоритет 3. Жизненный цикл векторного индекса

### Цель

Автоматически синхронизировать semantic/hybrid retrieval с изменениями корпуса.

### Планируемые работы

- ввести явные состояния индекса `ready`, `stale`, `rebuilding` и `failed`;
- помечать индекс устаревшим после успешного добавления или изменения чанков;
- запускать перестроение из фонового задания;
- объединять несколько близких запросов на перестроение;
- строить новый индекс во временном расположении;
- проверять manifest, контрольные суммы, размерность и соответствие базе;
- атомарно заменять рабочий индекс только после полной проверки;
- сохранять предыдущий рабочий индекс при ошибке перестроения;
- показывать состояние и диагностическое сообщение через API;
- сохранять exact retrieval доступным во время перестроения.

### Критерии готовности

- новая статья становится доступна semantic/hybrid search без ручной команды;
- частично построенный индекс никогда не обслуживает запросы;
- ошибка обновления не ломает exact search и предыдущий валидный индекс;
- после перезапуска состояние индекса восстанавливается однозначно;
- параллельные ingestion-задания не запускают конфликтующие перестроения.

## Приоритет 4. Фильтры и группировка результатов

### Цель

Сделать поиск управляемым на растущем корпусе и не заполнять выдачу множеством
чанков одной статьи.

### Планируемые работы

- определить доступные фильтры на основании реально хранимых метаданных;
- поддержать фильтрацию по статье, DOI, году, журналу, автору, разделу, типу
  источника, текстовому слою и пользовательским тегам там, где данные доступны;
- применять одинаковую семантику фильтров к exact, semantic и hybrid search;
- добавить группировку по статье;
- добавить ограничение числа чанков от одной статьи;
- сохранить исходные ранги и оценки чанков в диагностике;
- явно описать поведение при отсутствующих метаданных;
- добавить элементы управления фильтрами в интерфейс.

### Критерии готовности

- фильтры не возвращают результаты за пределами заданных условий;
- exact, semantic и hybrid одинаково интерпретируют фильтры;
- группировка не теряет ссылку на лучший фрагмент и страницу;
- снятие фильтров воспроизводит исходную выдачу;
- API остаётся детерминированным при одинаковом запросе и состоянии корпуса.

## Приоритет 5. Расширенный контекст результата

### Цель

Дать достаточно контекста для оценки релевантности до открытия всей статьи.

### Планируемые работы

- добавить получение полного текста найденного чанка;
- добавить предыдущий и следующий чанки в пределах той же статьи;
- добавить получение текста всей страницы;
- показывать диапазон страниц и границы выбранного фрагмента;
- подсвечивать совпадения запроса в представлении, не изменяя сохранённый текст;
- исключить переход контекста в соседнюю статью;
- задать ограничения на размер ответа и безопасную пагинацию.

### Критерии готовности

- соседний контекст принадлежит той же статье и правильной последовательности;
- исходный сохранённый текст остаётся неизменным;
- номера страниц согласованы с PDF;
- большие страницы и чанки не приводят к неограниченному ответу API;
- для отсутствующего соседнего чанка возвращается явное пустое значение.

## Приоритет 6. Таблицы, подписи, формулы и OCR

### Цель

Повысить полноту поиска по научным данным, которые обычное извлечение текста
может терять или искажать.

### Планируемые работы

- провести аудит корпуса по качеству текстового слоя;
- измерить долю страниц без текста и с подозрительно малым объёмом текста;
- проверить извлечение подписей к таблицам и рисункам;
- определить отдельные типы источников для таблиц и подписей, если это
  необходимо по результатам аудита;
- сохранить страницу и координаты `bbox`, когда extractor предоставляет их
  надёжно;
- определить диагностируемые правила выбора original/OCR text layer;
- улучшить обработку сканов без изменения оригинального PDF;
- добавить контрольные примеры с формулами, числовыми значениями, таблицами и
  подписями.

### Критерии готовности

- система явно сообщает, какой текстовый слой проиндексирован;
- найденные таблицы и подписи ведут на правильную страницу;
- OCR-ошибки не маскируются как успешная обработка;
- повторная обработка одного PDF воспроизводима при фиксированных версиях
  инструментов;
- изменения качества подтверждены evaluation-примерами.

## Приоритет 7. Масштабирование и производительность

### Цель

Сохранить приемлемое время ответа и устойчивость при росте числа статей и
одновременных запросов.

### Планируемые работы

- зафиксировать benchmark-корпус и сценарии измерений;
- измерить ingestion throughput, время построения индекса и latency поиска;
- кэшировать проверенный векторный индекс по checksum/manifest;
- определить корректную инвалидацию кэша;
- рассмотреть memory mapping для крупных локальных индексов;
- ввести верхние границы `top_k`, размера кандидатов и контекста;
- добавить пагинацию результатов;
- проверить одновременный search, ingestion и rebuild;
- оптимизировать только подтверждённые профилированием узкие места;
- документировать аппаратную конфигурацию каждого benchmark.

### Критерии готовности

- benchmark воспроизводится одной документированной командой;
- повторный поиск не загружает и не валидирует неизменный индекс без
  необходимости;
- API имеет ограниченные и предсказуемые размеры ответов;
- конкурентное обновление не выдаёт частичные данные;
- до и после оптимизации сохранены сопоставимые метрики.

## Приоритет 8. Расширенная evaluation поиска

### Цель

Измерять способность системы находить нужный источник для реальных вопросов,
а не только подтверждать работоспособность API.

### Планируемые работы

- расширить набор вопросов русскими и английскими формулировками;
- добавить парафразы, термины, формулы, числа, методы, таблицы и подписи;
- добавить вопросы без ответа в корпусе;
- хранить релевантность на уровне статьи и чанка;
- определить правила разметки и проверки gold data;
- сравнивать exact, semantic и hybrid на одном наборе;
- считать Recall@k, MRR, nDCG, Precision@k, покрытие статей и latency;
- отдельно измерять влияние фильтров и группировки;
- сохранять версию корпуса, индексный manifest и конфигурацию запуска;
- задать пороги регрессии для CI или локального release gate.

### Критерии готовности

- отчёт полностью воспроизводим по сохранённой конфигурации;
- каждая метрика имеет однозначное определение;
- вопросы без ответа не считаются успешными из-за случайного совпадения;
- регрессия качества или трассировки блокирует продвижение изменения;
- сравнение методов использует одинаковый корпус и одинаковую gold-разметку.

## Порядок выполнения

Рекомендуемый порядок фиксирован зависимостями:

1. доступ к PDF и найденной странице;
2. API загрузки и задания ingestion;
3. жизненный цикл векторного индекса;
4. фильтры и группировка;
5. расширенный контекст;
6. таблицы, подписи, формулы и OCR;
7. масштабирование и производительность;
8. расширенная evaluation поиска.

Приоритет 8 расположен последним как отдельный крупный этап, но небольшие
регрессионные тесты и новые evaluation-примеры добавляются в каждом предыдущем
приоритете. Нельзя откладывать проверку корректности до финальной стадии.

## Процесс работы над каждым приоритетом

Для каждого приоритета применяется один и тот же цикл:

1. проверить текущую реализацию и зафиксировать baseline;
2. подготовить подробный план только выбранного приоритета;
3. согласовать API, схему данных, миграции и критерии приёмки;
4. реализовать только согласованный объём;
5. выполнить модульные, интеграционные и регрессионные тесты;
6. провести smoke test на локальном корпусе;
7. обновить документацию и инструкции эксплуатации;
8. сформировать отчёт по изменениям, тестам и ограничениям;
9. создать отдельный commit после явного согласования этого действия;
10. остановиться перед следующим приоритетом и дождаться решения пользователя.

## Обязательный отчёт по этапу

Каждый завершённый приоритет должен иметь отчёт следующего вида:

```text
Changed:
- фактически изменённые компоненты и поведение

Tests run:
- реально выполненные команды и их результаты

Limitations:
- известные ограничения и непроверенные сценарии

Verdict:
- выполнены ли согласованные критерии готовности
```

## Первый следующий шаг

Первым этапом должен быть **Приоритет 1: доступ к PDF и найденной странице**.
До начала реализации для него необходимо подготовить и согласовать отдельный
технический план, основанный на текущих моделях данных, путях хранения PDF,
FastAPI endpoints и поисковом интерфейсе.
