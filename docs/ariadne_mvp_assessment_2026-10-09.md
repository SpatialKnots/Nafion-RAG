# ARIADNE MVP: состояние и предзаявочное снижение рисков

Дата: 9 октября 2026 года, Asia/Yekaterinburg.

## Вывод

Рабочая копия уже содержит технический MVP для ingestion, поиска и проверки источников. Это существенный задел для проекта. Полный продукт заявки — получение проверенных экспериментальных записей и сравнительной таблицы — пока не подтверждён.

Главный риск сейчас: неверная связь числа с образцом, свойством и условиями, а не отсутствие PDF-парсера или поиска. Следующая работа должна проверить эту связь на ограниченном домене, замкнуть review/export и измерить трудозатраты химика.

Это целевой аудит исходников и состояния среды, не полный аудит безопасности, всех строк кода, лицензий или научной корректности корпуса. Проверялась рабочая копия, включая незакоммиченные изменения, а не только Git HEAD.

## Что пока не закрыто для заявки

1. **Полная экспериментальная запись.** Текущий candidate хранит article/chunk, тип, field, lexeme, numeric value, unit, confidence и source. Нет полной связанной модели sample/property/conditions/method с evidence каждого поля и связи. Операторы, диапазоны и погрешности не восстановлены в полную структуру.
2. **Научная идентичность.** Лексические дубликаты не равны одному эксперименту. `10 nm` может быть scale bar; `55%` — выход синтеза; одинаковое число может относиться к разным образцам. Это уже показано source review, а не гипотетический риск.
3. **Scientific Verification Engine.** Есть lexical guards и cues. Нет доказанного общего контроля экспериментальных связей. Confidence 0.80/0.70/0.60 назначается по типу chunk, а не калиброванной вероятности правильности.
4. **Independent gold и сравнение B/C.** Предзаявочные KPI precision ≥90%, recall ≥60%, provenance 100%, abstention ≥85% и экономия времени ≥30% остаются целями. Нынешняя retrieval evaluation их не измеряет.
5. **Локальный полный workflow.** Embeddings локальны; `build_answer_provider` поддерживает runtime `openai`. Наличие тестового `ExtractiveAnswerProvider` не подтверждает автономный full-record extractor. Offline импорт → extraction → checks → review → export не проверен.
6. **Поставка и воспроизводимость.** Есть manifest индексов и snapshots, но рабочий MVP включает untracked исходники/тесты. В частности, context cues, review store/UI и тест review UI не возвращаются `git ls-files`. Чистый checkout HEAD не воспроизводит проверенный здесь состав. В просмотренном комплекте не установлены готовые lockfile/CI/лицензионный комплект; чистая установка и backup/restore не проверены.
7. **Полезность для химика.** Нет измеренного полного времени подготовки проверенной таблицы на независимой пользовательской задаче. Масштабирование и перенос на другую машину остаются отдельными проверками.

## Что делать сейчас: очередь с проверяемым результатом

### 1. Зафиксировать воспроизводимый baseline

Составить manifest выбранных исходников, тестов, схемы БД, runtime/dependencies и доступных model artifacts; отделить generated/temp от необходимых файлов. Сохранить текущие изменения, не коммитить весь каталог вслепую. Подготовить минимальный согласованный snapshot релиза и проверить запуск из него в отдельной среде.

**Готово, когда:** другой каталог/компьютер запускает выбранную версию, doctor и tests проходят; ясно, какие части требуют докачки/ключей. Секреты и закрытые PDF в публичный комплект не включаются.

### 2. Согласовать один сценарий и разметить 10–15 публикаций

Выбрать один тип проводимости и обязательные условия сравнимости. H-Nafion и Li-Nafion не объединять только из-за общей единицы. Схему gold хранить отдельно от production: sample, property, raw value/unit, operator/range/uncertainty, conditions, experimental/calculated/reference origin, evidence и статусы отсутствия/неоднозначности.

Размечать все подходящие записи внутри заранее ограниченного scope, включая не найденные поиском. Отдельные статьи оставить для оценки и не использовать для настройки; второму химику дать независимую разметку части источников.

**Готово, когда:** понятно, что считается одной записью и ошибкой, измерена плотность записей/время разметки, зафиксированы разногласия. Набор из 10–15 статей — pilot, не доказательство выполнения годовых KPI.

### 3. Замкнуть один полный вертикальный процесс

В отдельном экспериментальном хранилище получить полную предложенную запись из реального абзаца, затем простой таблицы. Каждый непустой field должен иметь точный source fragment; отсутствующее условие не заполняется догадкой. Использовать существующие ingestion/source-navigation/review компоненты.

Развести proposed, machine_checks_passed, needs_review и human_confirmed. Добавить исправление полей, историю, сохранение после перезапуска и JSON/CSV export полной записи. Старый numeric review оставить отдельной проверкой изменений extractor.

**Готово, когда:** химик проходит PDF → candidate → evidence → correction/rejection → подтверждённая таблица → export. Показать также неверный образец, пропущенное условие, диапазон и calculated/reference case.

### 4. Проверить эффект verification и трудозатраты

Сравнить B (фиксированный extractor) и C (тот же extractor + checks) при одинаковых parser/model/prompt/data. A (нынешний numeric extractor) сравнивать только по общим полям. D — процесс C с review химиком.

Измерять TP/FP/FN полной записи, recall с учётом detection losses, coverage, ложные допуски/отказы, ошибки по полям. Дубликаты не увеличивают recall. Сохранять версии и failures. Человеческое время включает поиск, чтение, исправления и export; одно машинное время не доказывает экономию труда.

**Готово, когда:** есть воспроизводимый сравнительный отчёт, а не только демонстрация удачных JSON. Рост precision при исчезновении почти всей coverage не считается достаточным доказательством пользы.

### 5. Закрыть автономность и эксплуатационные риски

Подобрать локальный extractor на имеющемся оборудовании для малого development опыта; измерить latency, память и throughput. Затем пройти полный workflow с отключённой сетью после установки. В изолированной копии проверить backup/restore, повторный импорт и прерывание worker, не повреждая рабочий корпус.

**Готово, когда:** один полный offline workflow и восстановление из backup подтверждены отчётами. Спецификацию будущей рабочей станции выводить из измеренных ограничений; закупка сама по себе не закрывает качество extraction.

## Предлагаемые ворота уверенности перед подачей

- Можно воспроизвести конкретную версию MVP.
- На реальных источниках получены полные записи с evidence и явными отказами.
- Review/export замыкают пользовательскую задачу.
- Пилот измерил ошибки и трудозатраты, включая сложные случаи.
- Локальная модель работает на доступном ресурсе; ограничения измерены.
- Есть второй химик и пользователь конкретного пилота.

План на ближайшие 2–4 недели возможен как ориентир при доступных химиках и модели; это не подтверждённый срок. Сейчас не требуется расширять scope графиками, новым доменом, промышленным корпусом или полноценной predictive-моделью.

## Отчёт об изменениях

Changed: аналитический документ и generated corpus/retrieval reports; исходники, production schemas, thresholds, facts и PDF не изменялись.

Tests run: результаты свежих проверок выше; новый полный OCR/recovery/offline эксперимент не выполнялся.

Limitations: unit tests, doctor и retrieval regression не заменяют независимую научную приёмку, продуктовый pilot или проверку чистой поставки.

Verdict: технический задел позволяет перейти к узкому full-record pilot. Научное качество результата заявки и автономная ARIADNE Box пока не доказаны.
