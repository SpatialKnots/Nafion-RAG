# ARIADNE: очередь исправлений после Fan/Doi/Besenhard

Дата: 13 ноября 2026. Статус: сохранено для возвращения позже.
Реализация всех пунктов ниже: **не начата**. Новые API-вызовы не выполняются.

Это основной план исполнения по итогам обсуждения с пользователем. Он уточняет
порядок работ из [аналитического разбора](fan_doi_besenhard_improvement_plan_2026-11-13.md):
сначала отдельный пакет небольших исправлений, затем потери контекста,
принадлежность фактов и полнота ответов. Анализ и исходные результаты сохраняются.

## Исходная точка

30 вопросов; после rewriting подготовлены 26 запросов вместо 6; реально выданы
22 ответа. Последующая качественная сверка: 11 с подтверждённым ядром, 7 с
неполнотой/проблемами формулировок, 4 с существенными расхождениями. Ещё 3 отказа
модели, 1 удержание guard и 4 отклонённых перевода составляют остальные исходы.
Оценка выполнена знакомым с набором ассистентом; общая независимая accuracy
не установлена. 50% = 11/22 с подтверждённым ядром, а не полностью правильных.

Серьёзность ошибки и трудоёмкость исправления оценивать отдельно. B6 —
серьёзная ошибка смысла с возможностью локального исправления. Потеря абзаца
может оказаться локальным дефектом, но место потери сначала нужно установить.
Ни один пункт пока не имеет подтверждённой оценки времени выполнения.

## Этап 0. Восстановить контрольную точку

- Прочитать этот план, аналитический разбор и фактический отчёт прогона.
- Проверить актуальный git diff и версии кода/PDF/index. Не предполагать, что
  рабочая среда осталась той же после перерыва.
- Сохранить исторические запросы, ответы, эталоны и diagnostics неизменными.
- Для новых сравнений создать отдельную версию артефактов. Для каждого пункта
  записывать статус, изменённые файлы, выполненные проверки, ограничения и вывод.

Готовность: понятно, с какой версией сравниваемся; исходы всех 30 учтены;
старые результаты и закрытые бюджеты сохранены. Затем начинать H1.

## Этап 1. Небольшие исправления — по одному, с отдельной проверкой

| ID | Проблема и действие | Критерий готовности | Граница исправления |
| --- | --- | --- | --- |

| H2 | B6: применить только визуально подтверждённое исправление диапазона 1.3–1.0 V в привязанном PDF-фрагменте | PDF SHA/страница/raw span/glyph mapping и журнал операции; исправленный вход; отрицательный контроль на настоящем ± | Не менять оригинальный PDF и raw extraction; не вводить глобальную замену ±; сравнение массы катода с ячейкой относится к S2 |

Порядок: H1 → H2 → H3 → H4. Для каждого — минимальная правка и проверки
затронутого поведения; затем проверка их совместимости. Один пункт можно
завершить независимо от остальных. Объединять всё в один релиз необязательно.

Для H3 сначала использовать сохранённые переводы и синтетические контроли
для проверки контракта. Эффект нового prompt требует новых реальных переводов
в отдельно зафиксированном будущем scope. Повторное чтение старого ответа
модели не является таким экспериментом.

## Этап 2. Вернуть необходимый контекст — S1

Случаи: F1/F7/D4/F8/D9; D8 отдельно как неполный контекст плюс смешение опытов.

1. Проследить нужный фрагмент: PDF → текст → chunk → кандидаты → ранжирование
   → отбор → дедупликация → actual prompt. При отсутствии исторического пула
   явно указать пробел; новый снимок не называть историческим.
2. Установить конкретный этап потери. Только после этого выбрать минимальную
   правку отбора, сохранения полного абзаца/таблицы или соседнего контекста.
3. До сравнения зафиксировать бюджет контекста/дополнительных чтений и условия
   остановки. Увеличение top_k без диагностики не считать решением.
4. Проверить все 30 случаев, включая сохранение полезного контекста D5/D7/B9.

Готовность: нужные полные source spans доходят до actual prompt либо выдана
точная причина недоступности; ложные совпадения по соседнему составу не дают
подтверждения. Это измерение покрытия контекста, ещё не правильности ответа.

## Этап 3. Исключить подмену научных фактов — S2

Случаи: F8/D8/D9/B6; D10 как отдельная проверка базы нормировки.

- Связать объект, величину, значение, единицу, состав, цикл/режим, базу
  нормировки, статус утверждения и supporting span. Обязательны только поля,
  существенные для конкретного вопроса; неизвестные не додумывать.
- Проверять различия: электролит/CEI; HFE/TFEE; первый/50-й цикл;
  катод/ячейка; измерение/DFT/прогноз; диапазон/неопределённость.
- Переиспользовать существующие evidence packet/claim checks там, где применимы.
  Их текущие структурированные проверки не объявлять общим автоматическим
  научным валидатором прозы.
- Начать офлайн с явных assertions и контролируемых подмен. Подключение к
  выдаче — отдельное решение после проверки обнаруженных ложных допусков и отказов.

Готовность: известные подмены выявляются, корректные контроли сохраняются,
unknown отличается от supported. Формат ссылки не считается доказательством.

## Этап 4. Полнота, терминология и смысловой перевод — S3

Случаи полноты/формулировок: F3/F4/F5/F9/D6/B7/B10. Случай перевода: F6.

- Выделить части исходного вопроса без значений из эталона. Для каждой части
  показывать подтверждённый ответ либо недостающие данные.
- Разделить отсутствие данных в prompt и пропуск имеющихся данных моделью.
  В F9 нужные энергии присутствовали; изменение поиска само по себе не решает
  такой пропуск.
- Проверить перевод non-dendritic mounds в F3 по оригинальному контексту.
  Локальное отображение термина может быть небольшим исправлением, но
  универсальный словарь без контекстной проверки не считать достаточным.
- Для F6 сохранить операцию «изменение сопротивления» и различие bulk/interfacial.
  Формальное сохранение Li/Mg из H3 эту смысловую проблему не решает.
- Соблюдать ранее принятые требования представления: вывод, условия,
  читаемые ссылки/страницы, подтверждающий фрагмент и существенные ограничения.

Готовность: офлайн-отчёт обнаруживает пропущенные части и смысловые подмены;
не требует деталей эталона, не запрошенных вопросом и не необходимых для смысла.
Успех новой генерации/перевода подтверждать только новым отдельным прогоном.

## Этап 5. D10 и проверка итогового кандидата — V1

1. После S2 рассмотреть расширение конечного контракта D10: энергия на массу
   катода, способ определения, условия и ограничения. Если контракт не
   обоснован, оставить удержание с уточнённой диагностикой H4.
2. Сравнить отдельные вмешательства офлайн; сохранить версии и взаимодействия.
   Выполнить необходимые unit/integration/regression проверки затронутых модулей.
3. Зафиксировать одного кандидата, настройки, prompts, code/PDF/index bindings,
   критерии оценки и concrete requests. Затем отдельно задать лимиты будущих
   model/OAuth-вызовов и политику повторов; старые allowances остаются закрытыми.
4. Известные 30 вопросов использовать для development/regression. Для проверки
   переноса подготовить отдельный набор на других статьях с закрытыми эталонами
   и независимой оценкой. Размер и разделение закрепить до получения ответов.

Отчёт: все 30 исходов; полнота; ошибки объекта/условий/единиц; поддержка среди
выданных и среди всех вопросов; отказы; удержания; usage и наблюдаемое время.
Для причинного вывода о приросте качества нужен сопоставимый baseline/candidate
протокол. Replay и синтетические тесты не считать новыми успешными ответами.

## Правила возобновления

- Текущая просьба пользователя — подготовить и сохранить план, вернуться позже.
  Она не запускает его реализацию, фоновые задания или новые API-вызовы сейчас.
- При возвращении начинать с этапа 0; далее H1–H4, S1, S2, S3, V1.
- Все пункты пока pending. Статус менять только после фактического выполнения;
  сохранять failures/diagnostics и отдельно указывать непроверенное.
- Не обещать заранее 80–90% качества или закрытие всех пунктов одним хотфиксом.
  Общий ранее записанный статус проекта остаётся 75%; новая accuracy не измерена.
